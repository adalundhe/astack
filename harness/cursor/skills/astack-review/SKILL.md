# Review

Split a change into risk-classified vectors, send blind adversarial reviewers from the user's approved `reviewer_pool` to break it, keep only reproduced findings, and stop adding reviewers to each vector only when the evidence says to.

1. **Define scope and load `reviewer_pool`:** review what the person specified; otherwise review all changes on the current branch since its base (including uncommitted edits). Read `reviewer_pool` (a JSON list of approved `{provider, model, effort}` entries) from `~/.config/astack/settings.json` (or `$XDG_CONFIG_HOME/astack/settings.json`). Never dispatch a model outside `reviewer_pool`—that list decides which vendors see the code. If `settings.json` has no `reviewer_pool`, treat the active session model as a 1-model pool and tell the person to run `/astack-setup`. Report any approved model that cannot be reached in the current harness under `COULD NOT TEST` rather than silently substituting another model.
2. **State the intent** (**run-it-back**): summarize what the change must do for users, based on the request, briefs, acceptance criteria, commits, and PR description.
3. **Cut the change into vectors and classify risk (no cap):**
   - A **vector** is a review lens (user-facing paths and acceptance criteria; failure modes, load, and concurrency; coding rules: **data-structures-first**, **no-implicit-states**, **no-hidden-flow-control**, **no-hidden-config**, **minimize-state-stores**, **check-your-boundaries**, **no-shared-writes**, **safe-to-rerun**, **no-bolt-ons**, **yagni**, **comment-cop**, **delight-users**, **no-picked-constants**, **event-driven**, **never-trade-functionality**), a slice of the implementation (a path or module group), or any other cut the lead chooses.
   - A slice is a **focus, not a blindfold**: every reviewer still receives the whole diff in its own worktree, the stated intent, and the reproduction folder, plus its assigned vector.
   - **Mandatory `seams` vector when sliced:** whenever you slice a change by path or module, add a `seams` vector covering interfaces and invariants between slices using the **blast-radius** method.
   - **Risk classification:** mark a vector **`risky`** if it touches any **lead** step 2 trigger (**shared interfaces, concurrency, persistence, auth/security, or a large diff**); otherwise mark it **`low`**. Risk determines how finely you cut vectors and how many models each vector starts with—never impose an arbitrary cap on the number of vectors or reviewers (**no-picked-constants**).
4. **Assign initial models and dispatch blind reviewers:**
   - A **`risky`** vector starts with **at least two** reviewers on **different** models from `reviewer_pool` (because the stopping estimate in Step 6 needs two). A **`low`** vector starts with **one**.
   - Whenever `reviewer_pool` allows, at least one reviewer per vector uses a model **other than the worker's**.
   - Keep reviewers on the same vector **blind to each other** until every reviewer in that batch finishes so they do not anchor on each other's findings.
   - Spawn each reviewer as the `astack-reviewer` subagent in the background (never substitute `generalPurpose`), passing its worktree/diff scope (with uncommitted edits copied in), assigned vector, stated intent, reproduction folder, astack `skills/` path (`..` from this skill, so it can read **adversarial-review** and every applicable coding rule directly), and its assigned `reviewer_pool` entry's `model` from `~/.config/astack/settings.json` (using `astack-reviewer` when Cursor can reach that model, or that entry's provider CLI such as `claude`, `codex`, `agy`, `cursor`, `gemini`, `devin` when cross-provider or unsupported; report any unreachable model rather than substituting).
   - Run `astack-check-gates <base>..<head>` across the full branch/PR range as a structural tripwire for deleted/renamed tests, skips, lint suppressions, downgraded assertions, loosened tolerances, or CI/lint config edits, and still audit test diffs semantically.
5. **Verify as findings arrive; combine findings, never vote:**
   - Rerun each finding's reproduction as soon as its reviewer finishes. Keep a finding only if the failure reproduces and violates the intent or an applicable rule; drop the rest, recording each reviewer's verified and dropped counts and drop reasons.
   - Merge verified findings by root cause, crediting every reviewer that surfaced each one. **Combine, never vote:** agreement between models counts for nothing—reproduction is the proof, so a reproduced bug found by only one model is just as real.
   - **Cross-vector findings still count:** if a reviewer discovers a verified bug whose root cause lives outside its assigned vector, file it under the vector where its root cause lives.
6. **Stop on evidence, per vector, with `astack-review-ledger`:**
   - After each reviewer's findings are verified, feed `reviewer_pool`, `worker_model`, declared `vectors` (with `low`/`risky` risk), and completed `reviews` (verified root-cause IDs filed by vector + dropped counts) into `astack-review-ledger` (`PATH` or `../../bin/astack-review-ledger`) instead of doing the math in prose.
   - Per vector, `astack-review-ledger` applies the stopping rule:
     - A **`low`** vector stops after one clean review (one reviewer and no verified bug filed under that vector by anyone). If a verified bug turns up under it—whether from its own reviewer or another vector's reviewer—add a reviewer on a different approved model and continue with the estimate below.
     - Otherwise, compare the new reviewer's verified root causes ($n_2$) against the union of earlier verified root causes on that vector ($n_1$), with overlap $m$: Chapman total $N = (n_1+1)(n_2+1)/(m+1) - 1$, $\text{unfound} = N - (n_1 + n_2 - m)$. Stop only when $\text{unfound} < 1$ **and** the estimate is informative ($m \ge 1$, or $n_1 = n_2 = 0$; one-sided zero is uninformative, so continue). Otherwise dispatch an unused model from `reviewer_pool` on that vector.
     - If `reviewer_pool` runs out while a vector cannot stop (including a single-model pool on any vector needing a second model), stop and **flag** it as `POOL EXHAUSTED` with its estimate—never stop silently.
7. **Report (coverage map first) and log counts to `LANES.md`:**
   - Open the report with the **Coverage map** produced by `astack-review-ledger --markdown`: each vector, its risk, the models on it, each reviewer's verified and dropped counts, the overlap and Chapman estimate, and why the vector stopped (`STOPPED (clean single review)`, `STOPPED (estimate)`, or `POOL EXHAUSTED`).
   - List vectors that were never assigned under `NOT ASSIGNED` and vectors that ran out of models under `POOL EXHAUSTED` (with estimate), beside `COULD NOT TEST` (including any approved model unreachable in this harness).
   - Follow with ranked findings (**adversarial-review**)—blockers first, then suggestions, then nits, each leading with user impact, reproduction, evidence, root-cause vector, and credited reviewers—followed by what was confirmed, what held, and what was dropped.
   - When running in an astack program with `LANES.md`, append `astack-review-ledger --lanes` lines logging verified and dropped counts per model and per vector to `LANES.md`.

Never modify the code under review. Hand findings back to the author (or, in an astack program, the lead turns them into lanes).
