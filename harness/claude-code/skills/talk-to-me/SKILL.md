# Talk to me

Explain an idea so the person gets it first time: the right terms, a picture, an example, an analogy.

Start from their files, code and words, not a summary. If their description could be more than one problem, name each with the sign that tells them apart, pick the likeliest, and say why.

1. **The point first:** what it is and why it matters to them, in a sentence or two.
2. **The field's terms** that would change what gets built, most important first: each in one plain sentence, with the part of their work it names and a real system, paper or project that uses it so, linked (**prove-it**).
3. **A picture:** the parts and how they connect, or the states (**show-the-states**), in Mermaid.
4. **A worked example,** from their own code or data where possible: real input, each step, real output.
5. **An analogy** in a sentence or two, and where it breaks. A neighbouring field that solved the same problem also lends its terms and prior art.
6. **What they haven't mentioned** that the field knows matters: its failure modes, limits and costs.
7. **Their description, rewritten** in the new words and still plain to an outsider. It feeds the brief, the plan or **research**.

Open every link and confirm it says what you cite it for; cut what you can't.
