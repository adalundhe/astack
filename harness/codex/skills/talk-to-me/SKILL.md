# Talk to me

Explain a concept, design, or result so the person grasps it on the first read. Use proper domain terms, a diagram, a worked example, and a short analogy.

**Scale depth to the question—skip sections that don't earn their keep.** A quick term lookup needs two crisp paragraphs, not a full essay.

Start from their actual files, code, and wording instead of a summary. When their description fits multiple problems, name each with its distinguishing symptom. Pick the likeliest one and explain why.

1. **Bottom line first:** state what it is and why it matters to their work in 1–2 sentences.
2. **Key domain terms:** list terms that change design choices, most important first. Give one plain sentence per term, map it to their code, and link to a primary system or paper.
3. **A diagram:** show components, data flow, or states (**show-the-states**) in Mermaid.
4. **A worked example:** use their own code or data when possible. Show concrete input, each step, and concrete output.
5. **A short analogy:** give a 1–2 sentence analogy plus where it breaks down, because unchecked analogies hide edge cases and cause bad mental models. Name adjacent fields that solved the same problem when their terms unlock useful prior art.
6. **Hidden pitfalls:** call out failure modes, limits, and costs practitioners know matter.
7. **Rewritten problem statement:** restate the problem in proper terminology while staying plain to an outsider, ready for a brief, plan, or **research-this**.

Open and verify every link you cite. Drop any link that does not directly support the claim.

**Done when:** the reader can act on the concept using accurate terms, verified links, and their own code context.

Referenced skills: `show-the-states` (`../show-the-states/SKILL.md`), `research-this` (`../research-this/SKILL.md`). Read any cited skill file before acting when its trigger applies.
