# Talk to me

Explain a concept, design, or result so the person grasps it on the first read: proper terms, a diagram, a worked example, and a short analogy.

Start from their actual files, code, and wording rather than a summary. If their description matches more than one distinct problem, name each with the distinguishing symptom, pick the likeliest, and explain why.

1. **Bottom line first:** what it is and why it matters to their work, in 1–2 sentences.
2. **Key domain terms** that actually affect design choices, most important first: one plain sentence each, mapped to the relevant part of their work, with a verified link to a real system, paper, or project using that term (**prove-it**).
3. **A diagram:** components and data flow, or states (**show-the-states**), in Mermaid.
4. **A worked example** using their own code or data where possible: concrete input, each step, concrete output.
5. **A short analogy** (1–2 sentences) plus where the analogy breaks down. Call out adjacent fields that solved the same problem if their terminology unlocks useful prior art.
6. **Hidden pitfalls:** failure modes, limits, and costs practitioners know matter that haven't been mentioned yet.
7. **Rewritten problem statement** using the proper terminology while staying plain to an outsider—ready to feed into a brief, plan, or **research-this**.

Open and verify every link you cite; drop any link that doesn't actually support the claim.
